# 1. Executive Summary

This document defines how AICORE Technologies Limited should present past, current, internal, pilot, and future projects as strong technical case studies and portfolio assets.

The goal is to move away from a weak portfolio style that only shows screenshots, logos, or generic project names. AICORE’s portfolio should prove that the company can design, build, integrate, and deploy practical intelligent systems across AI, automation, embedded systems, IoT, robotics, SaaS platforms, developer tools, mobile applications, technical training, and operational dashboards.

AICORE’s case studies should communicate:

* the real problem or operational challenge;
* the industry context;
* the system or platform built;
* the workflow before and after;
* the technical architecture;
* the services and products involved;
* the technologies used;
* the implementation approach;
* the outcome or expected value;
* the future improvement path;
* the reason the project demonstrates AICORE’s capability.

The strongest case-study message should be:

> **AICORE does not only build screens. AICORE builds complete intelligent systems that connect software, AI, firmware, devices, dashboards, workflows, data, and people.**

This document provides templates for:

1. Website case study pages.
2. Portfolio cards.
3. One-page case study summaries.
4. Proposal case study inserts.
5. Pitch deck case study slides.
6. Product build notes.
7. Internal project documentation.
8. AICORE Academy training case studies.
9. Prototype and pilot case studies.
10. GrowthOS-ready case study records.

The case study and portfolio system should support the redesigned AICORE website, especially the **Products**, **Solutions**, **Industries**, **Insights**, and future **Case Studies** sections.

# 2. Case Study Strategy

## 2.1 Why AICORE Needs Strong Case Studies

AICORE’s services are technical and cross-domain. Many visitors may not immediately understand the depth of the company’s capability from a service list alone. Case studies help convert broad claims into proof.

A strong case study can show that AICORE can:

* build AI-powered tools;
* automate business workflows;
* develop SaaS platforms;
* design embedded firmware;
* connect sensors to cloud dashboards;
* build mobile apps for operations;
* create robotics and STEM systems;
* build monitoring systems;
* create internal developer tools;
* train learners through practical technology programmes.

## 2.2 Case Study Role in the Website

Case studies should support the website in five ways:

1. **Credibility** — show real or realistic examples of systems AICORE can build.
2. **Education** — help prospects understand what a solution looks like in practice.
3. **SEO** — support search visibility for industry and technical use cases.
4. **Sales enablement** — give the business development team proof assets for proposals and outreach.
5. **Product validation** — show how AICORE-owned platforms solve practical problems.

## 2.3 Case Study Positioning Statement

Use this statement as a guiding principle:

> **Each AICORE case study should explain the problem, the system, the workflow, the technical approach, and the value—not just show the interface.**

## 2.4 Case Study Design Philosophy

Every case study should follow a problem-to-system-to-outcome structure.

```text
Industry Context
→ Problem
→ AICORE Solution
→ System Architecture
→ Workflow
→ Technologies
→ Deliverables
→ Outcome / Expected Value
→ Future Improvements
```

## 2.5 What Case Studies Should Avoid

AICORE case studies should avoid:

* showing only screenshots without explanation;
* vague statements such as “we built a platform” without describing the system;
* claiming production impact without evidence;
* overstating AI capability;
* hiding product maturity status;
* presenting prototype screens as production systems;
* mentioning client names without permission;
* publishing sensitive system details;
* making AICORE look like a generic website design company.

# 3. Types of Case Studies AICORE Can Publish

AICORE does not need to wait for only fully completed external client projects. The company can publish different types of case studies, as long as the status is clear and honest.

## 3.1 External Client Case Study

A public case study based on work completed for a client.

Use when:

* client has granted permission;
* project is complete or meaningfully deployed;
* screenshots and outcomes can be shared;
* the project strengthens AICORE’s positioning.

Status label:

> Client Project

## 3.2 Anonymized Client Case Study

A case study based on a real client project without naming the client.

Use when:

* client permission is limited;
* the industry and technical approach can be discussed;
* sensitive details must be removed.

Status label:

> Anonymized Client Project

## 3.3 Internal Product Build Note

A case study explaining an AICORE-owned product or internal platform.

Examples:

* AICORE GrowthOS;
* internal AI assistant;
* firmware simulator;
* device test dashboard;
* content automation system.

Status label:

> Internal Product Build

## 3.4 Product Platform Case Study

A case study about a reusable AICORE product/platform.

Examples:

* Throughport WMS;
* IoT Monitoring Platform;
* Smart Energy Monitoring Platform;
* Device Fleet Management Platform;
* AI Business Assistant Platform.

Status label:

> Product Platform

## 3.5 Prototype Case Study

A case study for a proof-of-concept or technical prototype.

Use when:

* the project proves feasibility;
* the prototype is not yet production-ready;
* lessons learned are useful;
* the technical architecture shows AICORE capability.

Status label:

> Prototype

## 3.6 Pilot Case Study

A case study for a project being tested with internal users, a partner, or selected users.

Use when:

* the system has been tested in a limited environment;
* feedback has been collected;
* the next development path is known.

Status label:

> Pilot

## 3.7 Training Programme Case Study

A case study showing AICORE Academy training delivery and learning outcomes.

Examples:

* robotics summer class;
* AI training for SMEs;
* embedded systems workshop;
* IoT practical bootcamp;
* school STEM programme.

Status label:

> Training Programme

## 3.8 Technical Experiment / Engineering Note

A technical case note showing an experiment, simulator, architecture, or engineering decision.

Use when:

* the work proves technical depth;
* the topic supports SEO;
* the content can feed developer/technical audience credibility.

Status label:

> Engineering Note

# 4. Case Study Selection Criteria

## 4.1 Projects Worth Turning Into Case Studies

AICORE should prioritize projects that demonstrate one or more of the following:

* AI applied to a real workflow;
* automation of a manual process;
* embedded or firmware development;
* IoT gateway or monitoring system;
* cloud dashboard or SaaS platform;
* mobile app connected to a backend or device;
* robotics or smart hardware prototype;
* smart energy monitoring;
* warehouse traceability;
* developer tool or simulator;
* technical training with practical learner outcomes.

## 4.2 Priority Case Study Themes

The highest-priority case study themes are:

1. AI business automation.
2. Embedded, IoT and sensor-to-cloud systems.
3. Smart energy monitoring.
4. Warehouse traceability and Throughport WMS.
5. AICORE GrowthOS.
6. Robotics and STEM training.
7. Developer tools and firmware simulation.
8. SaaS MVP and platform development.
9. Mobile companion apps for IoT or operations.
10. Industry-specific automation workflows.

## 4.3 Case Study Readiness Checklist

Before publishing a case study, confirm:

* the problem is clear;
* the industry context is clear;
* the system built is clear;
* the maturity status is honest;
* screenshots or diagrams are available;
* technical details are safe to share;
* client permission is confirmed if needed;
* outcomes are supported by evidence or framed as expected value;
* the CTA is relevant;
* the case study links to services, products, and industries.

# 16. Case Study Editorial Rules

## 16.1 Voice and Tone

Case studies should sound:

* technical;
* clear;
* practical;
* credible;
* business-aware;
* honest;
* outcome-oriented.

They should not sound:

* exaggerated;
* salesy;
* vague;
* overly academic;
* like a design portfolio only;
* like an unverified success story.

## 16.2 Writing Rules

Use:

* specific project names;
* specific problem statements;
* clear workflows;
* service/product tags;
* architecture diagrams;
* honest maturity labels;
* measurable outcomes only when available;
* expected value language where exact metrics are unavailable.

Avoid:

* “we transformed the business” without details;
* fake performance metrics;
* unsupported ROI claims;
* excessive buzzwords;
* client names without permission;
* sensitive technical details;
* generic website/design language.

## 16.3 Product Maturity Language

Use clear status labels:

* Concept;
* Prototype;
* MVP;
* Pilot;
* Production;
* Internal Use;
* Client-Ready;
* Productized Service;
* Training Programme.

## 16.4 Outcome Language

Use:

* “The system was designed to…”
* “The prototype demonstrated…”
* “The expected value is…”
* “The pilot helped validate…”
* “The platform supports…”
* “The training programme enabled learners to…”

Avoid:

* “guaranteed to…”
* “increased revenue by X%” unless verified;
* “fully automated everything”;
* “revolutionized operations” without evidence.

# 17. Client Permission and Privacy Rules

## 17.1 Permission Levels

| Level                  | Meaning                                                    | Public Use                                           |
| ---------------------- | ---------------------------------------------------------- | ---------------------------------------------------- |
| Full Public Permission | Client name, logo, screenshots, and results can be shared. | Full case study allowed.                             |
| Limited Permission     | Some details can be shared, but not all.                   | Partial or anonymized case study.                    |
| Anonymized Permission  | Client cannot be named.                                    | Use sector-only description.                         |
| Internal Only          | Cannot be published externally.                            | Use only for internal training/proposals if allowed. |
| No Permission          | Cannot be used.                                            | Do not publish.                                      |

## 17.2 Anonymization Rules

When anonymizing:

* remove client name;
* remove logos;
* remove exact locations if sensitive;
* remove user names;
* remove private business data;
* simplify architecture if needed;
* use general sector labels such as “a logistics company” or “a training institution.”

## 17.3 Sensitive Project Rules

Extra care is needed for:

* healthcare systems;
* energy/electrical systems;
* security and surveillance;
* finance/payment systems;
* government/public sector work;
* systems involving personal data;
* systems involving safety alerts or remote commands.

Do not publish sensitive details unless reviewed and approved.
