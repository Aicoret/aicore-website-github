# 1. Executive Summary

This Website UI/UX and Visual Direction Brief defines how the redesigned AICORE Technologies Limited website should look, feel, behave, and communicate visually.

The website must support AICORE’s repositioning from a generic website/software design company into a serious AI, automation, embedded systems, IoT, robotics, SaaS, developer tools, mobile applications, and intelligent systems company.

The visual direction should make AICORE feel like:

> **A practical technology engineering company that builds intelligent systems across AI, automation, software, firmware, embedded devices, IoT, robotics, dashboards, mobile apps, SaaS platforms, and technical training.**

The website must not feel like:

* a generic website design agency;
* a graphic design company;
* a cheap digital services vendor;
* a template-based software company;
* a vague AI hype website;
* a stock-photo-heavy corporate brochure;
* a portfolio site that only shows screens without explaining systems.

The strongest design direction is:

> **Clean technical interface + engineering credibility + system diagrams + product screenshots + restrained futuristic accents.**

The site should visually express the brand theme:

> **AI • Automation • Intelligent Systems**

This means the design should combine:

* strong typography;
* dark technical hero sections;
* clean white or off-white content sections;
* diagram-led explanations;
* product/platform previews;
* workflow and architecture visuals;
* meaningful service icons;
* industry use-case cards;
* practical screenshots and prototype mockups;
* clear CTAs;
* trust-building layout discipline;
* fast and accessible responsive implementation.

The homepage should immediately communicate that AICORE builds real systems, not ordinary websites. The hero section should use a system-style visual that combines AI nodes, cloud platform, embedded device, IoT sensor, dashboard, mobile interface, and automation workflow. Generic laptop mockups and stock office images should be avoided.

This document should guide the redesign of `aicoret.com`, including the homepage, Solutions, Products, Industries, Academy, Insights, About, Contact, service detail pages, product pages, industry pages, case study pages, and future lead-capture flows.

# 2. Design Strategy

## 2.1 Website Design Goal

The goal of the AICORE website design is to make visitors understand within the first few seconds that AICORE is a technically capable company that builds intelligent systems.

The design should help visitors answer:

1. What does AICORE do?
2. Why is AICORE different?
3. Which solutions does AICORE offer?
4. Which products and platforms is AICORE building?
5. Which industries does AICORE serve?
6. How can someone request consultation, a product demo, training, or a project discussion?

## 2.2 Strategic Design Positioning

The website should be positioned visually as:

> **A deep-tech, AI, automation, embedded, IoT, SaaS, robotics, and intelligent systems company website.**

It should use visual cues associated with:

* engineering systems;
* dashboards;
* connected devices;
* AI workflows;
* automation pipelines;
* intelligent monitoring;
* technical diagrams;
* operational interfaces;
* device-to-cloud architecture;
* practical technology training.

## 2.3 Design Personality

The visual personality should be:

| Attribute       | Visual Meaning                                                                              |
| --------------- | ------------------------------------------------------------------------------------------- |
| Technical       | Use diagrams, data cards, grid layouts, code/architecture hints, and system visuals.        |
| Practical       | Show workflows, dashboards, device monitoring, field use cases, and clear outcomes.         |
| Confident       | Use bold headlines, structured pages, strong CTAs, and disciplined spacing.                 |
| Clean           | Avoid clutter, excessive gradients, random animation, and too many colors.                  |
| Intelligent     | Use network visuals, AI panels, structured cards, and decision-support elements.            |
| Engineering-led | Use hardware, firmware, device, cloud, dashboard, and automation visual language.           |
| Business-aware  | Connect visuals to outcomes such as visibility, automation, monitoring, speed, and control. |
| Trustworthy     | Avoid exaggerated visuals, fake metrics, and unsupported claims.                            |

## 2.4 Design Principles

### Principle 1 — Communicate Systems, Not Just Screens

The website should not only show screenshots of web pages. It should show complete systems: inputs, devices, data, workflows, AI, dashboards, people, and actions.

### Principle 2 — Show Engineering Credibility Early

The first visible screen should make AICORE look technically capable. Use words and visuals such as AI systems, embedded firmware, IoT gateways, dashboards, robotics, automation pipelines, mobile apps, and SaaS platforms.

### Principle 3 — Use Diagrams as a Brand Asset

Architecture diagrams, workflow diagrams, sensor-to-cloud diagrams, AI workflow panels, and product modules should become part of AICORE’s visual identity.

### Principle 4 — Keep the Interface Professional and Readable

The site should feel modern but not noisy. Use strong typography, clear spacing, accessible contrast, and practical content hierarchy.

### Principle 5 — Avoid Generic Agency Design

Avoid generic hero mockups, abstract “digital transformation” visuals, agency-style gradients, random blobs, and stock photos of people pointing at laptops.

### Principle 6 — Use Visual Proof

Where possible, use product mockups, actual screenshots, prototype dashboards, architecture previews, diagrams, hardware photos, training photos, and case-study visuals.

### Principle 7 — Make Lead Capture Obvious but Not Aggressive

CTAs should be visible throughout the website, but the tone should remain consultative: Start a Project, Request Consultation, Request Demo, Discuss Your Idea, Explore AICORE Academy.

# 4. Color Direction

## 4.1 Color Strategy

AICORE’s color system should communicate technology, intelligence, trust, precision, and energy. The palette should support both dark technical sections and clean light content sections.

Recommended visual approach:

* dark navy / near-black for hero and high-impact technical sections;
* electric blue or cyan for AI, data, and intelligence accents;
* green or teal accent for automation, systems, and operational improvement;
* warm amber accent used sparingly for alerts, energy, academy, and highlights;
* white/off-white for readable body content;
* neutral grays for cards, borders, dividers, and supporting text.

## 4.4 Color Usage Rules

Use color with discipline:

* Primary buttons should use AICORE Blue.
* Secondary buttons can use white/transparent with border on dark sections.
* Cyan should be used for data, AI, and connector accents.
* Teal should signal automation, IoT monitoring, and successful operational flow.
* Amber should be used sparingly for energy, warnings, or highlighted metrics.
* Do not use too many bright colors in one section.
* Do not make every card different colors.
* Use colors consistently by meaning.

## 4.6 Dark Mode vs Light Mode

The public website does not need a user-toggle dark mode in the first version. Instead, use intentional dark sections and light sections.

Recommended pattern:

* dark hero;
* light service sections;
* dark product showcase band;
* light industry cards;
* dark CTA/footer;
* light article/content pages.

This gives a modern technical feel without making the full site visually heavy.

# 5. Typography Direction

## 5.1 Typography Strategy

Typography should be modern, readable, technical, and confident. Avoid decorative fonts. Use a strong sans-serif family for headings and body text.

## 5.2 Recommended Font Direction

If using free web fonts:

| Role                             | Recommended Font Options                 |
| -------------------------------- | ---------------------------------------- |
| Headings                         | Inter, Sora, Manrope, Space Grotesk      |
| Body                             | Inter, Manrope, Source Sans 3            |
| Technical Labels / Code Snippets | JetBrains Mono, IBM Plex Mono, Fira Code |

Recommended pairing:

* Headings: **Sora** or **Space Grotesk**
* Body: **Inter**
* Technical labels: **JetBrains Mono**

Alternative safer pairing:

* Headings and body: **Inter** only
* Technical labels: **JetBrains Mono**

## 5.3 Heading Style

Headings should be bold, direct, and spacious.

Recommended sizes for desktop:

| Element         | Size Range |  Weight |
| --------------- | ---------: | ------: |
| Hero headline   |    56–72px | 700–800 |
| Page headline   |    44–60px | 700–800 |
| Section heading |    32–44px |     700 |
| Card heading    |    20–26px | 600–700 |
| Body text       |    16–18px | 400–500 |
| Small labels    |    12–14px | 500–600 |

Recommended sizes for mobile:

| Element         | Size Range |
| --------------- | ---------: |
| Hero headline   |    36–44px |
| Page headline   |    32–40px |
| Section heading |    26–32px |
| Card heading    |    18–22px |
| Body text       |       16px |

## 5.4 Typography Rules

* Use short, strong headlines.
* Avoid long headings that wrap awkwardly.
* Use muted supporting text for explanation.
* Use monospace only for technical labels, code-like tags, protocol names, or dashboard metadata.
* Keep line height generous for readability.
* Avoid all-uppercase long headings.
* Use uppercase only for small badges, labels, or category chips.

# 6. Layout System

## 6.1 Layout Philosophy

The website should use a clean grid-based system. The layout should feel precise, technical, and uncluttered.

Recommended base layout:

* max content width: 1180–1280px;
* generous section padding;
* 12-column desktop grid;
* 2-column and 3-column card layouts;
* single-column mobile layout;
* sticky or fixed top navigation only if performance remains smooth;
* strong visual hierarchy between hero, content, proof, products, and CTAs.

## 6.2 Spacing System

Use consistent spacing tokens:

| Token | Approx. Value | Usage                          |
| ----- | ------------: | ------------------------------ |
| XS    |           4px | Icon gaps, small dividers.     |
| SM    |           8px | Inline spacing, badge padding. |
| MD    |          16px | Card internal spacing.         |
| LG    |          24px | Card gaps, form groups.        |
| XL    |          32px | Section inner spacing.         |
| 2XL   |          48px | Major section gaps.            |
| 3XL   |          72px | Desktop section padding.       |
| 4XL   |          96px | Large hero/feature spacing.    |

## 6.3 Section Rhythm

Recommended page rhythm:

1. Hero section
2. Trust/positioning strip
3. Explanation section
4. Solutions or product cards
5. Visual proof / diagram
6. Industry or use-case cards
7. How AICORE works
8. CTA section
9. Footer

Each section should have a clear role. Avoid repeating similar card grids without a new purpose.

## 6.4 Card Design

Cards should be clean, slightly elevated, and technical.

Recommended card style:

* background: white or dark translucent on dark sections;
* border: 1px solid soft border;
* radius: 16–24px;
* shadow: subtle, not heavy;
* icon or label at top;
* clear heading;
* short description;
* feature tags or use-case bullets;
* CTA link where relevant.

## 6.5 Recommended Layout Components

Use reusable sections/components:

* HeroSection
* SectionHeader
* SolutionCard
* ProductCard
* IndustryCard
* ProcessStep
* SystemDiagram
* FeatureGrid
* DashboardPreview
* TechnologyTagCloud
* CTASection
* Testimonial/ProofBlock later
* CaseStudyCard later
* ContactForm

AICORE’s imagery should reinforce practical engineering. Use a mix of:

* product screenshots;

* technical diagrams;
* embedded boards and device photos;
* IoT gateway illustrations;
* sensor-to-cloud visuals;
* robotics and STEM training photos;
* energy monitoring charts;
* warehouse/operations visuals;
* team/project photos if available;
* carefully selected technical stock imagery only where needed.

## 7.2 Visual Themes to Use

Use visuals such as:

* dashboard previews;
* product UI screenshots;
* architecture diagrams;
* workflow diagrams;
* IoT network graphics;
* device and cloud diagrams;
* warehouse process maps;
* energy monitoring charts;
* AI workflow panels;
* mobile interface previews;
* embedded board illustrations;
* sensor-to-cloud diagrams;
* robotics kits and hardware photos;
* academy training photos;
* code/editor snippets used lightly.

## 7.3 Visual Themes to Avoid

Avoid:

* generic laptop mockups with no context;
* random stock photos of people in offices;
* vague futuristic AI heads or glowing brains;

* agency-style illustrations;
* fake customer dashboards that imply unavailable features;

* robotic imagery that looks like unrelated sci-fi.

If a product is not fully built, label visuals honestly:

* Concept mockup;
* Prototype screen;
* Sample dashboard;
* Simulated data;
* Architecture preview;
* Early MVP screenshot.

Do not present simulated screens as live production screenshots.

The homepage hero should use one of these options:

Show a layered dashboard preview with small connected device cards around it:

* energy chart;
* warehouse movement card;
* mobile app preview;
* embedded device status.

### Option C — Split Hero

Left side: headline and CTAs. Right side: clean technical illustration combining AI node, cloud, sensor, dashboard, and device.

### Option D — Engineering Collage

Use a disciplined collage of real system elements:

* embedded board;
* sensor;
* dashboard;
* code block;
* mobile app;
* robotic arm/kit;
* cloud connector.

This should be clean and not look cluttered.

# 8. Diagram Direction

## 8.1 Why Diagrams Matter

Diagrams should be a major part of AICORE’s website because they show that AICORE understands systems, workflows, architecture, and implementation.

Diagrams should make the website feel like a technical engineering company, not a generic agency.

## 8.2 Diagram Types to Use

### 1. AI Workflow Diagram

Example:

```text
Business Data → AI Analysis → Recommended Action → Human Review → Workflow Execution → Report
```

Use for AI Systems and GrowthOS-related sections.

### 2. Sensor-to-Cloud Diagram

Example:

```text
Sensor / Meter / Device → Gateway → Cloud API → Dashboard → Alerts → Mobile App
```

Use for IoT, energy, agriculture, manufacturing, and facilities.

### 3. Business Automation Workflow

Example:

```text
Request → Classification → Approval → Notification → Task → Report
```

Use for automation pages and SME use cases.

### 4. Warehouse Traceability Flow

Example:

```text
Receive → Verify → Store → Move → Pick → Dispatch → Report
```

Use for Throughport and logistics/warehousing.

### 5. Product Platform Architecture

Example:

```text
Users → Web/Mobile Interface → API → Database → AI/Automation/Provider Integrations
```

Use for Products and SaaS pages.

### 6. Edge AI Diagram

Example:

```text
Camera → Edge Device → AI Detection → Event Log → Alert → Dashboard
```

Use for security, manufacturing, inspection, and computer vision.

### 7. Academy Learning Flow

Example:

```text
Learner → Practical Module → Project Build → Assessment → Certificate → Portfolio
```

Use for Academy pages.

## 8.3 Diagram Style Rules

* Use clean nodes and connector lines.
* Use icons inside nodes where useful.
* Use subtle gradients only for highlights.
* Use short labels.
* Avoid overly complex architecture drawings on the public site.
* Make diagrams responsive.
* Provide alt text for accessibility.
* Use the same visual language across all diagrams.

## 8.4 Diagram Visual Style

Recommended style:

* rounded rectangles;
* thin connector lines;
* small icons;
* dark text on light diagrams;
* glowing cyan/blue connector accents on dark diagrams;
* numbered steps for workflows;
* optional small status chips such as AI, API, IoT, Dashboard, Alert.

# 11. Homepage Structure

## 11.1 Homepage Goal

The homepage must quickly communicate:

* AICORE is not a generic website/design agency.
* AICORE builds AI, automation, embedded, IoT, robotics, SaaS, mobile, and intelligent systems.
* AICORE has clear service pillars.
* AICORE has products/platforms.
* AICORE serves real industries.
* AICORE Academy is part of the company’s technical capacity-building identity.
* Visitors can start a project, request consultation, or request a demo.

## 11.2 Recommended Homepage Section Order

### Section 1 — Hero

Purpose: Immediate repositioning and strongest brand statement.

Suggested content:

* Badge: `AI • Automation • Intelligent Systems`
* Headline: `Engineering AI-Powered Software, Automation and Intelligent Systems`
* Subtext: `AICORE Technologies builds AI tools, business automation platforms, embedded firmware, IoT systems, robotics solutions, SaaS products, developer tools, and mobile applications for organizations that want to operate smarter.`
* Primary CTA: `Start a Project`
* Secondary CTA: `Explore Our Solutions`
* Visual: system architecture hero or dashboard/device composite.

Design expectations:

* dark technical background;
* strong headline;
* visible CTAs;
* system diagram or technical product visual on the right;
* subtle grid/noise pattern;
* small service tags under CTAs.

Purpose: Explain the company in one concise section.

Suggested layout:

* 3 or 4 horizontal cards:

  * AI-powered tools;
  * automation platforms;
  * embedded/IoT systems;
  * SaaS/mobile/intelligent platforms.

Design expectations:

* clean card grid;
* icon + short explanation;

### Section 3 — Solutions Overview

Purpose: Present the eight service pillars.

Cards:

1. AI Systems and AI Tools
2. Process and Business Automation

Animation should be subtle, useful, and performance-friendly. AICORE should not use excessive motion that makes the site feel like a generic tech template.

## 14.2 Recommended Motion

* small pulse on AI/data nodes;
* smooth accordion expansion;
* button hover transitions;
* animated counters only if real metrics exist.

## 14.3 Motion to Avoid

Avoid:

* excessive parallax;
* spinning 3D globes unless very polished and lightweight;
* heavy particle backgrounds;
* random floating shapes;
* animations that delay content reading;
* fake live dashboards with misleading movement.

* CTAs should be visible and predictable.
* Dropdowns should be easy to use on desktop and mobile.
* Cards should indicate clickability.
* Forms should validate clearly.
* Mobile menu should be simple.
* Do not hide important content behind complex interactions.

# 15. Responsive Design Expectations

## 15.1 Breakpoint Strategy

Recommended breakpoints:

| Device  | Width Range | Layout Expectation                                     |
| ------- | ----------: | ------------------------------------------------------ |
| Mobile  |   320–767px | Single column, large tap targets, simplified diagrams. |
| Tablet  |  768–1023px | 2-column cards, stacked hero.                          |
| Laptop  | 1024–1279px | Full layout, 2–3 columns.                              |
| Desktop |     1280px+ | Wide layout, richer diagrams, larger hero.             |

## 15.2 Mobile Rules

* Hero should stack: text first, visual second.
* Diagrams should simplify into vertical flows.
* Navigation should use hamburger menu.
* CTAs should be full-width or large enough to tap.
* Card grids should become single column.
* Forms should be single column.
* Tables should become cards or horizontally scroll only where unavoidable.
* Text should remain readable without zoom.

## 15.3 Tablet Rules

* Use 2-column card grids.
* Product visuals may stack.
* Diagrams can remain but should reduce node count.
* Use medium section padding.

## 15.4 Desktop Rules

* Use full hero layout with text and system visual.
* Use 3- or 4-column cards where appropriate.
* Use diagrams and product previews more prominently.
* Keep content max-width controlled.

# 16. Accessibility Expectations

## 16.1 Accessibility Baseline

The website should follow practical accessibility rules:

* sufficient color contrast;
* semantic HTML headings;
* alt text for images and diagrams;
* keyboard navigable menus and forms;
* visible focus states;
* form labels and error messages;
* no important information communicated by color alone;
* readable font sizes;
* captions or descriptions for complex diagrams.

## 16.2 Contrast Rules

* Text on dark background must be high contrast.
* Muted text should still be readable.
* Cyan text on dark background should be tested for readability.
* Do not use low-contrast gray text for important content.

## 16.3 Diagram Accessibility

For diagrams:

* provide alt text;
* include a short text explanation near the diagram;
* avoid tiny labels;
* ensure mobile users can read the flow.
